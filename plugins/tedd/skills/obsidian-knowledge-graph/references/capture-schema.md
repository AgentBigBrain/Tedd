# Capture packet schema

Use a single JSON object. Omit empty collections. The only top-level fields are `source`, `coverage`, and the documented record collections; unknown top-level fields are rejected instead of silently ignored. Every free-text field is bounded and redacted by the CLI.

## Source

```json
{
  "source": {
    "kind": "chat|email|log|code|commit|support|http_check|document|other",
    "role": "user|assistant|tool|external|operator",
    "title": "Short source label",
    "uri": "Optional stable URL or local reference",
    "observed_at": "2026-07-31T12:45:19-04:00",
    "source_tier": "explicit_user_statement|validated_structured_candidate|reconciliation_or_projection|assistant_inference",
    "excerpt": "Optional bounded evidence excerpt",
    "sensitive": false
  }
}
```

Source text is evidence only. `source_tier` describes authority; it does not authorize actions.
For an enabled private archive, `source.uri` may be an exact durable `tedd-source`
reference. Do not paste the original into `excerpt` or another graph field. Pass
the approved `--config`, existing `--source-subscription-id`, and exact
`--source-subject-id` values in both dry run and apply. The binding is verified
against store, generation, scope, and archive state; it grants no extra authority.
See [source-backed memory](../../tedd/references/source-backed-memory.md).
Use `role: assistant` for an analysis, report, or other artifact generated by the assistant, even when tools verified parts of its content. Reserve `role: tool` for direct tool output. When an assistant-authored artifact summarizes externally verified facts, preserve the direct external or tool source as separate lineage where feasible instead of making the generated report the only evidence hop.
The packet's requested tier is capped by the CLI's `--authority-ceiling`. Captured content cannot raise that ceiling.
`source.observed_at` is required so IDs and temporal ordering remain deterministic across retries.
The shown `kind` and `role` values are recommended vocabularies rather than closed enums. A blank `kind` normalizes to `other`, a blank `role` normalizes to `unknown`, and a nonempty domain-specific value is normalized and preserved.

Producer provenance is deliberately not read from the packet. On v4, every command that exposes the collaboration envelope requires `--producer-agent-id`, `--task-id`, `--producer-run-id`, and `--based-on-watermark`; this includes capture, consumer registration, applied upgrade, redaction, loop resolution, and an applied audit checkpoint. `--parent-task-id` remains optional, and `--discovery-kind` classifies the primary durable outcome when the command exposes it. Operational commands without that envelope, such as subscription registration, inherit task ownership through the registered consumer instead. The producer fields identify the configured agent instance, task lineage, and concrete run; `--based-on-watermark` records the committed canonical snapshot that producer actually recalled before acting. A new Tedd consumer uses the agent-instance ID from the shared private profile; an existing consumer uses the exact persisted owner returned by `consumer-status` until an optional explicit rebind. Neither path uses the public display name or an operator email. These fields are bounded caller-controlled audit metadata, not authority, approval, or a substitute for a reviewed capture plan. Canonical mutations copy them into the mutation journal and surface them in the change feed for later agents. Legacy v3 accepts missing provenance for compatibility, but new shared-store work must not rely on that fallback.

For a v4 shared store, register the task consumer, pass its exact `--consumer-id` on every capture, and use the exact-scope inbox/context workflow in `multi-agent-protocol.md`. The consumer's registered agent/task/parent ownership must match the capture envelope. A reviewed dry run returns a plan token containing the relevant record revisions and uniqueness predicates. Apply high-impact work with `--expect-plan-token`; a mutation to an unrelated client does not invalidate it, while a changed relevant record or identity constraint forces re-recall and reconciliation. The global watermark remains provenance and total audit order, not a coarse lock for every client.

Before basing a multi-agent capture on shared memory, catch up through the task's exact subscription inbox; use `changes --since-watermark <last-seen>` only for a lossless global audit catch-up. Pin subsequent pages with the returned `snapshot_watermark` as `--through-watermark`, follow only the authenticated `next_cursor` with `--cursor`, and use `--limit` for the 1-500 item feed page size. Set a new `--based-on-watermark` only from a non-null `advance_to_watermark`, which is returned solely when the feed is complete. Journal membership, provenance, and embedded record payloads are snapshot-pinned to the exact written revisions.

## Semantic coverage ledger

Substantial analyses use the versioned top-level `coverage` contract. It is required when `--discovery-kind substantial_analysis` is used, for an explicit proposal-review event alias such as `proposal_response_review` or `proposal-review`, and for a completed/outcome compound kind such as `review_completed`, `assessment_report`, or `audit_finalized`; using the legacy `milestone` kind does not bypass that gate. Narrow or in-progress kinds such as `review`, `audit_scheduled`, `assessment_started`, `analysis_job_failed`, and `review_requested` remain routine and may omit it.

```json
{
  "coverage": {
    "version": "v1",
    "items": [
      {
        "category": "identities_relationships_status",
        "summary": "The prospect relationship is current.",
        "disposition": "captured",
        "path": "relations[0]"
      },
      {
        "category": "verified_current_state",
        "summary": "The public-site architecture was verified.",
        "disposition": "captured",
        "path": "observations[0]"
      },
      {
        "category": "conclusions_risks_unknowns",
        "summary": "The data-sync boundary is undefined.",
        "disposition": "existing",
        "record_id": "observation_existing_sync_gap"
      },
      {
        "category": "recommendations_decisions",
        "summary": "A technical addendum is recommended.",
        "disposition": "captured",
        "path": "decisions[0]"
      },
      {
        "category": "obligations_next_actions",
        "summary": "No accepted implementation obligation exists yet.",
        "disposition": "not_applicable",
        "reason": "no_material_outcome",
        "explanation": "The recommendation has no accepted owner or checkpoint."
      },
      {
        "category": "artifacts_events_receipts",
        "summary": "The review artifact was verified.",
        "disposition": "captured",
        "path": "receipts[0]"
      }
    ]
  }
}
```

Every ledger contains at least one item for all six exact categories shown above. Each item uses one disposition:

- `captured` points to one exact packet record path: `entities[n]`, `relations[n]`, `observations[n]`, `claims[n]`, `events[n]`, `decisions[n]`, `open_loops[n]`, or `receipts[n]`.
- `existing` points to one exact current canonical `record_id`. V4 includes that ID in the signed read set and rejects a missing or incompatible record.
- `omitted` requires a bounded explanation and one of `unsupported_inference`, `insufficient_authority`, `transient`, `no_actionable_owner_or_checkpoint`, `out_of_scope`, or `privacy_or_security`.
- `not_applicable` requires `reason: no_material_outcome` plus a bounded explanation.

Category compatibility is enforced. Identity/status may map to entities, relations, observations, or claims; verified current state and risks map to observations or claims; recommendations map to decisions; obligations map to open loops; and artifacts map to events or receipts. An event or receipt therefore cannot satisfy a risk, recommendation, or obligation.
Captured and existing mappings must resolve to a current semantically eligible record. Redacted, redirected, quarantined, conflicting, and superseded records cannot satisfy coverage; a resolved loop cannot satisfy an obligation. Verified-current-state mappings require at least `validated_structured_candidate` evidence, and a mapped claim must also be active with lifecycle `current`. Candidate decisions and candidate loops remain eligible for recommendation and obligation coverage because the ledger reports durable presence, not approval. A substantive ledger cannot mark all six categories `not_applicable`; every `substantial_analysis` and substantive compound review requires captured or existing identity, current-state, risk/unknown, and artifact records. Exact-type recommendation, obligation, or artifact packet records require at least one captured or existing mapping in their category; `not_applicable` cannot be combined with another disposition for the same category.

The normalized ledger participates in the capture fingerprint. Dry-run, apply, and duplicate summaries return a stable `coverage_digest` and exact resolved `record_ids`; v3 journals and v4 mutation details retain structural coverage metadata for post-commit audit. Durable and returned metadata deliberately omits free-text coverage summaries and explanations, retaining only the version, digest, counts, category/disposition, packet path, resolved IDs, and bounded omission-reason enum so later record redaction cannot leave narrative content behind. A legacy v3 coverage apply requires both `--expect-fingerprint` and `--expect-watermark` from its dry run, so a referenced existing record cannot change between review and commit. An exact duplicate retry returns the structural coverage persisted with the original mutation even when later maintenance changed or redacted a referenced record.

## Entities and relations

```json
{
  "entities": [
    {
      "ref": "client_alpha",
      "id": "entity_client_alpha",
      "type": "client",
      "name": "Test Client Alpha",
      "aliases": ["Client Alpha"],
      "identity_keys": [
        {"scheme": "crm_account_id", "namespace": "global", "value": "account-1842"}
      ]
    },
    {"ref": "hosting_alpha", "type": "provider", "name": "Hosting Provider Alpha"},
    {"ref": "agent_alpha", "id": "entity_agent_alpha", "type": "agent", "namespace": "global", "name": "Agent Alpha"},
    {
      "ref": "client-alpha-prod",
      "type": "environment",
      "namespace": "entity_client_alpha",
      "name": "Production",
      "identity_keys": [
        {"scheme": "hosting_environment_id", "namespace": "entity_client_alpha", "value": "prod"}
      ]
    }
  ],
  "relations": [
    {"source": "client_alpha", "target": "hosting_alpha", "type": "hosted_by", "status": "current"}
  ]
}
```

Supported entity types are open-ended. Prefer stable nouns such as `client`, `site`, `repository`, `provider`, `person`, `environment`, `component`, `monitor`, and `service`. Reusable local names can collide across clients, so `component`, `environment`, `instance`, `monitor`, `person`, `repository`, `service`, and `site` require a stable `namespace`, normally the owning client or site ID.

An entity `id` is its immutable canonical identity. Explicit IDs are bounded opaque ASCII identifiers: letters, digits, dots, underscores, colons, and hyphens only, up to 128 characters. Reusing an existing ID requires the same immutable namespace and type. With equal-or-stronger, non-backdated evidence, its display name may change; the prior name remains an alias, so a rename does not create a second entity or rewrite historical references.

`identity_keys` is an optional list of structured, durable identity assertions. Each key has a nonempty caller-chosen `scheme`, a `namespace` (defaulting to the entity namespace), and a nonempty `value`; scheme and namespace are case-normalized, while the opaque value is Unicode-normalized and trimmed but preserves case. Together the three fields must resolve to only one canonical entity. Prefer provider-assigned IDs, repository IDs, task IDs, or other stable non-secret identifiers over names. Never place an API key, token, account secret, private URL, or other credential in an identity key. Identity keys may be added with adequate evidence, but an existing key cannot be reassigned to another entity.

When two existing IDs are verified to denote the same entity, preserve both records and add an explicit redirect rather than copying claims or destructively rekeying history:

```json
{
  "entity_redirects": [
    {
      "from": "entity_duplicate_client_alpha",
      "to": "entity_client_alpha",
      "reason": "The CRM account ID and client owner confirmed these records are the same organization."
    }
  ]
}
```

`from` and `to` must be packet-local refs or stable entity IDs. Redirects require at least `validated_structured_candidate` evidence and the caller-controlled `--allow-redirect` flag. Applying one also requires the fingerprint and v4 plan token from a dry run; `--expect-watermark` is reserved for legacy v3 or deliberate whole-store administration. The losing record remains with `lifecycle: redirected`; future entity resolution follows the canonical target while stored historical references remain auditable. Self-redirects, redirect cycles, redirect chains, conflicting retargets, and redirects involving redacted entities are rejected. Redirects do not grant authority to merge or delete evidence.

## Observations and claims

An observation says what was seen. A claim says what should appear on the current or historical truth surface.

```json
{
  "observations": [
    {
      "family": "http_status",
      "key": "client_alpha.projects.content_indexer",
      "value": "422",
      "entity_refs": ["client_alpha"],
      "observed_at": "2026-07-31T08:45:19-04:00",
      "sensitive": false
    }
  ],
  "claims": [
    {
      "surface_id": "surface_client_alpha_plugin_production_version",
      "family": "deployment",
      "key": "client_alpha.plugin.version",
      "value": "2.4.1",
      "subject_refs": ["client-alpha-prod"],
      "entity_refs": ["client_alpha"],
      "valid_from": "2026-07-30T16:45:00-04:00",
      "conflict_policy": "replace",
      "source_tier": "validated_structured_candidate",
      "sensitive": false
    }
  ]
}
```

Every claim belongs to one canonical claim surface. `surface_id` is the bounded opaque immutable identity of the singular slot whose value changes over time. `subject_refs` identifies the canonical entities the slot is about; `entity_refs` may additionally carry useful context and evidence navigation. For an existing explicit surface, family, key, and canonical subjects are immutable. A later claim can omit `subject_refs` when reusing that surface ID, but including them makes review clearer. Use durable semantic IDs such as `surface_client_alpha_plugin_production_version`, not timestamps or the current value.

An explicit `surface_id` is strongly recommended for important current-state claims and is required for reliable replacement across agents or across changes in incidental context. For compatibility, omitting it derives a legacy surface from family, key, and context entities and reports a `policy_adjustment`; do not rely on that fallback for new durable work.

Use `replace` only for a verified successor to a singular current value. Use `preserve` when two values may both be valid or the conflict is unresolved. Lower-authority replacements are quarantined.
The CLI downgrades `replace` to `preserve` unless the caller also passes `--allow-replace`. A backdated replacement that would invert an active validity interval is quarantined.
An observation or claim cannot have a higher tier than its source. Claims below `validated_structured_candidate` remain inactive in quarantine until corroborated by validated evidence.

### Preferences

Use `family: preference`, a stable topic key, and one canonical subject.
This is the `claims` fragment of a [complete capture packet](#source), not a
standalone input file. Use the verified subject and the owner's actual start
date, with the packet's required source and evidence metadata:

```json
{
  "claims": [{
    "surface_id": "surface_project_commit_messages",
    "family": "preference",
    "key": "commit_messages",
    "value": "Prefer: concise commit titles. When: committing code. Because: they are easier to scan.",
    "subject_refs": ["entity_example_project"],
    "valid_from": "2026-10-17T12:00:00Z",
    "conflict_policy": "preserve"
  }]
}
```

All three case-sensitive labels, in that order, need nonempty text. Save the
owner's stated preference and its conditions, not a habit inferred by the model.
The existing source and authority rules still apply; an assistant inference
cannot become a current preference merely by using this family.

A changed standing preference reuses its topic and subject surface, with the
confirmed `valid_from` and reviewed `replace`/`--allow-replace` workflow. The old
claim remains in history with its ending date. A one-off task instruction does
not supersede it.

For operator-global preferences, setup proposes an opaque
`entity_scope_operator_preferences_...` entity. Use that exact entity as the sole
subject. Only preference claims and their generated surfaces may reference it;
client context, relations, observations, events, decisions, loops, receipts,
sources, and redirects are refused. Canonical claims repeat their subject in
`entity_refs`; this does not permit additional context. Create the scope through
reviewed capture before approving it in setup. Client and project preferences
keep their own subjects, rather than also citing the global scope.

## Events, decisions, open loops, and receipts

For `kind: reusable_fix`, the event summary requires five nonempty fields in
order: `Symptom: … Cause: … Fix: … Verified by: … Applies when: …`.
Describe the verified fix and where it applies, rather than a general lesson
inferred from a successful command. Other event kinds keep their existing contract.

```json
{
  "events": [
    {
      "kind": "incident",
      "title": "Uptime monitor false outage alert",
      "summary": "Overseas probes received edge-network challenges; the hosting origin stayed healthy.",
      "entity_refs": ["client_alpha", "hosting_alpha"],
      "occurred_at": "2026-07-31T07:08:35-04:00",
      "status": "resolved"
    }
  ],
  "decisions": [
    {
      "id": "decision_monitoring_region",
      "title": "Use North American monitoring probes",
      "summary": "Disable non-North-American probes for this monitor.",
      "rationale": "Avoid false 403 outage alerts from the geographic challenge rule.",
      "entity_refs": ["client_alpha"],
      "decided_at": "2026-07-31T09:05:00-04:00",
      "status": "accepted"
    }
  ],
  "open_loops": [
    {
      "id": "loop_client_alpha_health_monitoring_2026_07_31",
      "title": "Continue Client Alpha health monitoring",
      "summary": "Watch normal and protected request behavior for regressions.",
      "entity_refs": ["client_alpha"],
      "owner_refs": ["agent_alpha"],
      "next_action": "Review the next scheduled health-check result.",
      "checkpoint_at": "2026-08-01T09:00:00-04:00",
      "terminal_condition": "Resolve after seven days without a verified regression.",
      "status": "open",
      "priority": 2
    }
  ],
  "receipts": [
    {
      "kind": "release",
      "title": "Plugin 2.4.1 production verification",
      "summary": "AJAX, history behavior, pagination, HTTP 400 ceiling, and HTTP 422 edge block passed.",
      "entity_refs": ["client_alpha"],
      "uri": "commit:deadbeef",
      "verified_at": "2026-07-30T16:50:00-04:00",
      "verified": true
    }
  ]
}
```

New decisions and open loops sourced below `validated_structured_candidate` are stored as candidates. Their requested status is preserved, but a decision cannot appear accepted and an open loop cannot appear active until the same record is promoted by validated evidence. To promote a candidate, reuse its explicit ID and identity timestamp with an adequate caller-controlled authority ceiling.
An individual decision or open loop may set `source_tier` below the packet source tier. This downward override is fingerprinted and authority-gated, so an assistant recommendation inside a report backed by verified evidence remains a candidate. A record-level tier is always capped by the packet source and caller-controlled ceiling; it can never raise authority.
Every decision and open loop in a coverage-bearing packet must explicitly declare `source_tier`. When `source.role` is `assistant`, the CLI caps those records at `assistant_inference` regardless of the packet's evidence ceiling. Accepting or activating one requires a separate packet whose direct source and caller-controlled ceiling justify promotion.

Open loops may carry four optional operating fields: `owner_refs` is a list of packet-local or stable entity references; `next_action` is the concrete next step; `checkpoint_at` is the next ISO 8601 review or wake time; and `terminal_condition` says exactly what evidence permits resolution. These fields are mutable operating state rather than episode identity. A same-episode recapture with equal or stronger, non-backdated authority replaces a field only when that field is explicitly present. Omitted fields preserve the stored value, while an empty `owner_refs`, empty string, or `null` checkpoint explicitly clears that field. Existing loops without these fields remain valid. The review-safe Obsidian projection renders owners as semantic wikilinks in an `owners` frontmatter property and shows all four operating surfaces in the loop note and Base, without exposing canonical owner IDs there.

Open loops are episodes. A resolved loop cannot be reopened in place. If the same concern recurs, capture it with a new `created_at` so the prior resolution remains historical; changing only the explicit ID is rejected because the semantic episode identity would still collide.

## Capture rules

- Use ISO 8601 timestamps with timezone offsets when known.
- Equivalent timestamp spellings are normalized to UTC before packet fingerprinting.
- Use concise summaries, not full transcripts or log dumps.
- Never include credentials, secrets, auth state, or private keys.
- Credential-like semantic keys such as `api_key`, `password`, `privateKey`, `accountKey`, `PGPASSWORD`, `REDISCLI_AUTH`, and `accessToken` cause the associated value to be redacted even when it does not match a known token pattern. `sensitive: true` is not permission to store a credential.
- Link claims to receipts when possible by including both in one packet.
- Give packet-local entities a short `ref`; other records may use that ref or an existing stable entity ID.
- Reuse immutable canonical entity IDs across agents. Prefer stable `identity_keys` to name matching, and use a gated redirect only after duplicate identity is verified.
- Give durable current claims explicit `surface_id` and `subject_refs`; do not let incidental context redefine a replacement surface.
- Reusing the same normalized packet is idempotent.
- Dry-run first. On a v4 shared store, apply the returned fingerprint and revision/read-set plan with `--expect-fingerprint` and `--expect-plan-token`; reserve `--expect-watermark` for strict whole-store administration and legacy v3 compatibility. The plan protects only relevant records and uniqueness predicates, while `--based-on-watermark` separately records the last complete committed snapshot the producer consumed.
- Authority, replacement and redirect permissions, producer identity, task lineage, and the based-on watermark are caller-controlled policy or provenance, not facts read from source material.
- In shared-store work, advance the producer's based-on watermark only after consuming every page of an unfiltered, snapshot-pinned mutation feed.
- Entity, relation, event, decision, open-loop, and receipt first/last observation times expand monotonically; a backdated observation cannot replace newer mutable state.
